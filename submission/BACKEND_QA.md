# 審査員に聞かれたときの答え方（バックエンド編）

「これはどんなバックエンドで動いているの？」「Google Cloudは何に使っているの？」と聞かれたときに、そのまま話せるようにまとめた資料です。数字と言い回しは、この版のコードと画面に合わせています。

## 30秒で答えるなら

> 画面も計算も、Cloud Runで動いています。サービスは2つです。誰でも見られる公開サービスと、IAMで守った非公開サービスです。
> 住民の事情メモや報告文を読んだり、次の一手を決めたりするときだけ、公開サービスが非公開サービスを呼びます。そこでVertex AIのGemini 3.5 Flashが、12人の事情メモを「誰がどの避難所を避けるべきか」に、報告文を「どの道路が通れないか」に読み替え、エージェントの次の一手を選びます。
> ただし、計画が本当に成り立つかどうかはAIに決めさせていません。自分で書いた決定論的なシミュレーター（Simulation Core）が、道路・時間・定員・期限から計算します。Geminiの答えは、公開側でもう一度シミュレーターに流し直して、一致したものだけを表示します。
> 判断はすべて、run_id付きでCloud Loggingに残ります。

画面では、プレイ画面の下にある「**Google Cloud上の処理の流れ**」を指させば、同じ流れを実際の値つきで見せられます。

## 全体の図

```text
 ブラウザ（プレイ画面）
   │  報告文 or 通行止めにする道路
   ▼
 Cloud Run 公開サービス  disaster-agentic-mvp（asia-northeast1、ログイン不要）
   │  ・画面とAPIを配信。Vertex AIの権限は持たない
   │  ・「AIなしで比較」はここでルール方策が判断（AIを使わない）
   │  IDトークンで認証（Cloud Run IAM、run.invoker だけ）
   ▼
 Cloud Run 非公開サービス  disaster-agentic-orchestrator（外から直接呼べない）
   │  ① 報告の読み取り：報告文 → 通れない道路のID（Gemini 1回）
   │  ② エージェントのループ：観測 → 判断（Gemini）→ 実行（道具）→ 検証（Core）を最大6回
   ▼
 Vertex AI  Gemini 3.5 Flash（構造化出力。返せるのは決まった選択肢だけ）

 Simulation Core（自作・決定論）：両方のサービスに入っていて、計画の成否を計算する
 Cloud Logging：非公開サービスが1ステップごとに構造化ログ（run_id で追跡）
```

## 「Geminiで計画を立て直す」を1回押すと起きること

1. **報告の読み取り**：ブラウザが報告文（例：「橋が冠水して渡れない」）を公開サービスに送ります。公開サービスは、その街の道路の一覧（ID・日本語名・つなぐ場所）と一緒に、非公開サービスへ渡します。Geminiは「どの道路が通れないか」を、**その街の道路IDの中からしか選べない形**（列挙型）で、最大2本返します。
2. **世界を作る**：その道路を通行止めにした世界を、公開サービスが組み立てます。
3. **エージェントのループ**：非公開サービスで、Geminiが状態を見て次の一手を選びます。選べる手は状態で決まっていて、たとえば計画が不成立なら「修復」か「人へ引き継ぎ」だけです。修復・弱点探し・代替計画づくりは道具（アルゴリズム）が行い、結果は毎回Simulation Coreが検算します。
4. **再検証**：返ってきた判断の記録を、公開サービスがもう一度Simulation Coreに流し直します。観測も結果も結論も完全に一致したときだけ、画面に表示します。
5. **表示**：地図・判断の記録・裏側の経路（モデル名、呼出し回数、時間）が出ます。run_idは画面には出さず、APIの応答とCloud Loggingに残ります。

## よくある質問

**Q. Google Cloudはサーバーを置いているだけでは？**
A. 4つを役割ごとに使っています。

| サービス | 役割 |
|---|---|
| Cloud Run | 公開と非公開の2つ |
| Vertex AIのGemini | 報告の読み取りとエージェントの判断の2役 |
| Cloud Run IAM | サービス間の認証。公開側はAIの権限を持たない |
| Cloud Logging | 全ステップの記録 |

Geminiを止めると、報告文から道路を読み取る機能は動きません。

**Q. 実在の人の事情を扱うなら、個人情報は？**
A. このデモの住民はすべて架空です。事情メモはGeminiに読ませるだけで、ログには件数しか残しません。実際の運用では、障害・病気・DV被害などは要配慮個人情報にあたるので、自治体の個人情報の取り扱い（本人の同意、扱える職員の限定、保存場所）を決めてからでないと使えません。ここは実用化に向けた課題です。

**Q. 「犯罪が起きやすい人」を判定しているの？**
A. していません。避難所での盗難や性被害、DV加害者と同じ避難所になる危険は、守られるべき人の側の条件（所在を守る、夜間の安全）として扱います。人に危険の印を付ける機能はありません。名前・年齢・性別・国籍・出身・宗教・言語だけから事情を推し量らないよう、Geminiに指示しています。

**Q. 人種や国籍、文化圏で避難先を変えているの？**
A. 変えていません。住民のデータには出身・国籍・宗教・人種の項目自体がありません。言葉・食事・礼拝などの配慮は、本人が書いた事情（「日本語の放送は分からない。ベトナム語なら分かる」「宗教上の理由で豚肉は食べられない」）としてだけ扱います。海外出身でも、メモに必要なことが書かれていなければ条件は付きません（テストで確かめています）。

**Q. 100人の一括検算は何をしているの？ AI？**
A. AIは使いません。架空の住民100人から12人ずつ選んだ30通りを、職員の設定でまとめて検算します。全員の避難先が決まるのは15通りで、決まらない理由（合う避難所がない人・定員不足）と、避難所に何を足せば救えるか（設備を1つ足す、定員を2人増やす）を計算で出します。3つを順に足すと28通りまで救えます。合成データ上の数字で、現実の避難所の評価ではありません。

**Q. ただのスライドでは？**
A. トップページはプレイ画面です。報告文を自分で書いたり、地図の道路を壊したりすると、毎回サーバーで計算し直します。スライドは説明用に別ページ（`/slides`）に分けています。

**Q. Geminiは何をしているの？ ルールで十分では？**
A. 2つあります。

1. **報告文の理解**：「小学校の前で土砂崩れ」を「小学校への道」に結びつけるのは、言い換えや表記ゆれがあるので、ルールでは難しい部分です。
2. **次の一手の選択**：こちらはルールでもできます。だから画面に「AIなしで比較」を置いて、正直に比べられるようにしています。

方針は「**AIには言葉の理解と判断を任せ、成否の判定は任せない**」です。

**Q. なぜ判定をAIにさせないの？**
A. 制約の多い計画では、LLMは「もっともらしいが成り立たない」計画を出しやすいからです。旅行計画のベンチマーク（TravelPlanner）では、GPT-4が全条件を満たしたのは0.6%でした。LLMの外に検証器を置く構成（LLM-Modulo）が提案されていて、EvacWeaveはその考え方です。

**Q. エージェントらしさはどこ？**
A. 観測・判断・実行・検証のループを、止めどきも含めて自分で回すところです。

- 何をするかを自分で選びます：修復、弱点探し（道路を1本ずつ止めて試す）、代替計画づくり。
- いつ止めるかも自分で決めます：完了するか、人に引き継ぐか。
- 救えない人がいるときは「完了」と言わず、どの道路が失われると何人が避難できないかを添えて人に渡します。

**Q. プロンプトインジェクションは？**
A. 報告文は「データ」としてGeminiに渡し、指示には従わないようにしています。さらに、Geminiが返せる値の型を、その街の道路IDの選択肢（最大2本）だけに絞っています。おかしな指示を書かれても、起きるのは「道路の読み違い」までです。

- 読み取った道路は画面に表示されます。
- その先の計画は必ずシミュレーターが検算します。
- 報告文そのものはログに残さず、文字数だけを記録します。

**Q. 暴走やコストの対策は？**
A. 上限を何重にもかけています。

| 項目 | 上限 |
|---|---|
| 1回の実行 | 最大6ステップ、Gemini最大6回 |
| 報告の読み取り | Gemini1回 |
| 同時実行 | 1件 |
| 1日の回数 | 40回まで（読み取りと実行の合計） |
| 1人あたり | Geminiを使う依頼は10分6回・1日9回、全員合わせて1時間15回、APIは1分60回 |
| Cloud Run | 使わないときは0台、最大1台 |

モデルは安価なGemini 3.5 Flashで、思考は「低」（エージェントの判断は「最小」）です。1日の上限まで使い切っても、概算で最大3ドル強です。請求側にも支出上限を設定します。

**Q. セキュリティは？ 大量アクセスや情報漏えいは？**
A. 応用情報技術者試験・OWASP Top 10の観点で点検し、結果を [docs/SECURITY.md](../docs/SECURITY.md) にまとめました。重大な問題はなく、見つかった中程度の問題は修正済みです（1人で1日のAI枠を使い切れる点、キャッシュを押し出して再計算させられる点）。APIキーは使っておらず、全コミットの履歴にも鍵はありません。残る対策（ロードバランサーとCloud Armor、非公開サービスの受け付けを内部だけにする設定）は費用と設定変更を伴うので、運用者の判断で行います。

**Q. 本番で個人情報（マイナンバーなど）を扱えるの？**
A. このデモのままでは扱いません。本番は、インターネットから切り離した庁内のネットワーク（三層分離のLGWAN接続系）に置き、マイナンバーや氏名は持たず、仮の番号・地点・避ける避難所と理由だけを扱う設計です。計画は平時に作って検算し、紙の計画や防災行政無線などの一方向の手段で届けます。外から入ってくる入口を作らないので、攻撃の的になりません（[docs/SECURITY.md](../docs/SECURITY.md) の2章）。

**Q. 失敗したらどうなる？**
A. 止まって記録します（fail closed）。

- Geminiが許可されていない手を選んだときや、壊れた出力を返したときは、その場で停止します。
- 時間切れのときも同じです。
- 画面では「Geminiの実行に失敗したのでルール方策の結果を表示します」と明示します。

**Q. 本当にGeminiが動いている証拠は？**
A. 3つ見せられます。

1. 画面の「Google Cloud上の処理の流れ」に出るモデル名と呼出し回数。APIの応答（`trace.run_id`）にはrun_idが入っています。
2. 同じrun_idのCloud Loggingの記録（`scripts/check_live_ai.py` が検索コマンドを表示します）。
3. リポジトリの `data/evidence/recorded_gemini_run.json`（記録したGeminiの実行。公開画面は再検証に通った場合だけ表示）。

**Q. 可観測性は？**
A. 各ステップの観測・許可された手・Geminiの選択・検証結果を、構造化ログでCloud Loggingに出しています。ログはrun_idと、リクエストのトレースIDで、公開側と非公開側をつなげて追えます。APIの応答にも全ステップの記録が入っています。

**Q. なぜADKやAgent Builderを使わないの？**
A. このエージェントの中心は「許可される手を状態から決めるガード」と「全ステップを再生して検証できること」です。そのため、ループを小さく自前で書きました。方策は差し替えられる作りなので、ADKなどに載せ替える余地はあります。

**Q. 実データは？ 実際に使えるの？**
A. いまは合成データ（2名と12名の街）だけです。現実の安全や避難判断は保証しませんし、避難指示も出しません。実用に向けては次の作業が要ります。

- 自治体の道路・避難所データの取り込み
- 担当者による評価
- 部分的な救出計画（今は全員を救える計画か、人へ引き継ぐかの二択）

**Q. 何が自作で、何が既製品？**
A. 分けると次のとおりです。

| 区分 | 中身 |
|---|---|
| 自作 | Simulation Core、エージェントのループとガード、修復・弱点探し・代替計画の道具、画面 |
| 既製品 | FastAPI、Pydantic、Google Gen AI SDK、Gemini（Vertex AI）、Cloud Run |

## 言わない方がいいこと（誇張しない）

- **「Geminiが避難計画を作る」とは言いません。** 計画を作るのは決定論的な道具（修復アルゴリズム）です。Geminiは報告を読み、どの道具をいつ使うか、いつ止めるかを選びます。
- **「AIが安全を判定する」とは言いません。** 判定するのはSimulation Coreで、それも合成データ上の成否です。
- **「AIなしで比較」を押した結果をGeminiの結果として見せません。** そちらはルール方策です。
