# セキュリティ — いまの守りと、本番での置き方

EvacWeaveのデモは、誰でも試せるようにインターネットに公開しています。扱うのは**すべて架空の合成データ**で、個人情報は一切ありません。この文書では、①公開デモがいま何を守っているか、②テストで何を確かめているか、③実際の自治体で使うなら、どこに・どう置くべきか、を分けて書きます。

## 1. 公開デモの守り（いま動いているもの）

| 守りたいもの | いまの対策 | 確かめているテスト |
|---|---|---|
| 費用（Geminiは有料） | 公開サービスはVertex AIの権限を持たず、IAMで保護した非公開サービスだけがGeminiを呼ぶ。1日の回数上限（Cloud Storageに1日1つの記録。条件付き書き込みで二重に数えず、読めなければ呼ばない）、同時1件、Cloud Runの最大1インスタンス、請求の上限設定 | `tests/test_live_agent.py`、`tests/test_live_quota.py` |
| 可用性（大量アクセス） | 送り元ごとの回数制限：APIは1分60回。Geminiを使う依頼は1人10分6回・1日9回、全員合わせて1時間15回まで。超えたら429と待ち時間（`apps/api/rate_limit.py`。送り元はGoogleの受付が付けたアドレスで、IPv6は/56ごと）。本文の大きさの上限（例：事情メモの依頼は8KB）、計算の上限（修復の探索は1回5万状態まで）。計算結果は使い回し、知らないシナリオ名はキャッシュに入れない（押し出して再計算させる攻撃を防ぐ）。一括検算は1回だけ計算する。画面のスクリプトはブラウザに5分保存させる | `tests/test_rate_limit.py`、`tests/test_public_pages.py`、`tests/test_live_agent.py` |
| 秘密情報・権限 | APIキーを使わない。認証はサービスアカウントとIDトークンだけで、リポジトリ（全コミットの履歴を含む）に鍵はない。IDトークンは非公開サービスの宛先にしか送らず、リダイレクトは追わない。非公開サービスの有料の診断は運用者だけが使え、サービスアカウント（公開サービスを含む）からは403 | `tests/test_live_agent.py`、`tests/test_gemini_calls.py` |
| 入力の改ざん・注入 | すべての入力を厳格な型（余分な項目は拒否）で確かめる。事情メモや報告文はGeminiに「データ」として渡し、答えの形は住民・避難所・道路のIDと決められた理由の列挙だけ。返った答えは非公開側と公開側の両方で確かめ、計画の成否は必ずSimulation Coreが計算する | `tests/test_care.py`、`tests/test_report_reader.py` |
| 画面の改ざん（XSS） | 画面はサーバーやメモの文字を文字列として表示し、HTMLとして解釈しない。Content-Security-Policyで外部スクリプトとインラインスクリプトを禁止。そのほかのセキュリティヘッダーも全応答に付ける | `tests/test_public_pages.py`（HTMLとして書き込む書き方を使っていないこと） |
| 情報の漏れ | 事情メモ・報告文・Geminiの答えはログに残さず、件数だけを記録する。SDKのエラーメッセージ（応答本文を含む）も記録しない。画面に内部の番号や版を出さない | `tests/test_gemini_calls.py`、`tests/test_care.py` |

### 点検の結果（2026-10-14）

応用情報技術者試験・OWASP Top 10の観点で、コードと設定を読んで点検しました（外部への通信はしていません）。重大（高）な問題はありませんでした。見つかったものと対応は次のとおりです。

| 重さ | 見つかったこと | 対応 |
|---|---|---|
| 中 | 1人で1日のGemini枠（40回）を約1時間で使い切れた。IPv6は/64ごとに別人と数えたため、家庭の回線1本で256人分になった | 済：1人1日9回、全員で1時間15回の上限を追加。IPv6は/56ごとに数える |
| 中 | 知らないシナリオ名を送ると、キャッシュから正しい結果が押し出され、一括検算（約1秒）を何度も計算させられた | 済：知らない名前はキャッシュの手前で断る。一括検算は同時に来ても1回だけ計算する |
| 中 | 公開サービスは最大1インスタンスなので、多数のアドレスから同時に来ると混雑する | 一部済：スクリプトをブラウザに保存させて依頼を減らした。根本的には、前段にロードバランサーとCloud Armor（多数のアドレスからの攻撃を止める）を置く。費用と設定変更を伴うので、運用者の判断で行う |
| 低 | 非公開サービスの有料の診断を、公開サービスのアカウントからも呼べた | 済：サービスアカウントからは403 |
| 低 | 回数制限で断ったときのログに、長いURLがそのまま残り、ログの量を増やせた | 済：パスを48文字で切る |
| 低 | GitHubからのデプロイ手順が、実行用アカウントを指定せず、環境変数も消していた（今は使っていない） | 済：Cloud Shellと同じデプロイスクリプトを使う形に揃えた |
| 低 | 非公開サービスは、受け付け口がインターネット全体に開いたまま（IAMで認証は必須）。1日の上限は公開側だけ | 残：受け付けを内部だけにする（`--ingress internal` と公開サービスのVPC経由の送信）。ネットワークの設定変更を伴うので、運用者の判断で行う |
| 低 | 依存ライブラリのバージョンを範囲で指定しており、ハッシュでの固定や脆弱性の自動点検がない | 残：`pip-compile --generate-hashes`、コンテナイメージのダイジェスト固定、pip-auditの追加 |
| 情報 | 正規表現による処理の遅延（ReDoS） | 問題なし：量指定子の入れ子がなく、入力の検査はRustの線形時間エンジン |
| 情報 | 費用の見積もりで、事情の読み取りの出力上限が古い値（2048）だった | 済：8192トークンで計算し直した（`infra/cloud-run/COST_GUARD.md`） |

## 2. 本番での置き方：インターネットを通らない構成

公開デモの構成は、そのまま自治体の本番には持ち込みません。要配慮個人情報（障害・病気・DV被害など）を扱う以上、**「外から入ってこられる入口を作らない」**ことを最優先にします。考え方は緊急地震速報に近く、計画は閉じた場所で作り、届けるときは一方向にします。

### 2.1 データを持たない（最小化）

- EvacWeaveは**マイナンバーを使いませんし、持ちません**。計画づくりに必要なのは「住民ごとの仮の番号」「住んでいる地点」「避けるべき避難所と理由」だけです。
- 氏名・住所・マイナンバーは、自治体の既存システム（マイナンバー利用事務系）に置いたままにします。仮の番号と本人の対応表もそちらに残し、EvacWeaveには渡しません。結果を本人に結びつけるのは、権限のある職員が庁内で行います。
- 事情メモも、AIが読んだあとは「避ける避難所と理由」の決まった形（列挙）に置き換わります。いまのデモと同じく、メモの本文はログに残しません。

こうしておけば、万一EvacWeave側から情報が漏れても、そこには番号と地点と理由しかなく、個人は特定できません。

### 2.2 置き場所：庁内の閉じたネットワーク

- 総務省のガイドラインは、自治体のネットワークを「マイナンバー利用事務系」「LGWAN接続系」「インターネット接続系」に分けるよう求めています（三層分離）。EvacWeaveは**LGWAN接続系**、つまりインターネットから切り離された側に置く想定です。
- Simulation Core（判定）と修復の探索（計画づくり）は決定論の計算だけで動き、**インターネットがなくても動きます**。いまのコードのまま、庁内のサーバーで動かせます。
- 事情メモを読むAIも、外へ出さずに動かします。
  - 庁内のサーバーで公開モデル（Gemmaなど）を動かす。
  - Google Distributed Cloudのエアギャップ版で、インターネットから切り離したままGeminiを動かす（2025年8月に一般提供）。
  - AIを使えない場合でも、職員が設定した条件で計画は作れます（デモの「AIなしで比較」と同じ仕組み）。

### 2.3 届け方：一方向（緊急地震速報と同じ考え方）

- 計画は平時に庁内で作り、Simulation Coreで検算しておきます。弱点ごとの代替計画も、このときに作ります。
- 住民へは、受け手からの接続を受け付けない一方向の手段で届けます。
  - 紙の個別避難計画
  - 防災行政無線
  - 緊急速報メール
  - 避難支援者への事前の共有
- 住民の端末からEvacWeaveに入ってくる入口がないので、外からの大量アクセス（DoS）や不正侵入の的になりません。
- 発災時に通信が止まっても、事前に配った計画と代替計画は手元に残ります。報告の読み取りと計画の作り直しは、災害対策本部の職員が庁内の端末から行います。

### 2.4 いまのデモのままでは使えない点

点検で、実データ（要配慮個人情報）を扱うなら必ず変える点も確かめました。

1. 事情メモを返すAPI（`GET /v1/agent/care`）は認証がありません。架空のデータだから公開しています。実データでは、職員の認証と、自治体ごとの見られる範囲の制限が必要です。特に「所在を守る」という条件は、DV被害を受けていることを示します。
2. Geminiの処理場所は既定で `global` です。国内で処理させ、データの扱いの契約条件も確かめる必要があります。閉域で動かすなら、この点は2.2の構成で解決します。
3. メモの検査は制御文字の禁止だけです。氏名や12桁の番号が書かれても気づきません。AIに渡す前に、個人を特定できる情報を検出して止める仕組み（Sensitive Data Protectionなど）が必要です。マイナンバーは法律で決められた事務以外では扱えないので、そもそも入力させない設計にします。
4. 本人の同意などの法的な根拠、アクセスの監査ログ、保存期間と削除の規程が必要です。なお、メモを保存もログ記録もしない今の作りは、そのまま活かせます。

### 2.5 運用で守ること（自治体の規程に合わせる）

- 職員ごとのアカウントと二要素認証。事情を見られる職員を限定する。
- 操作ログの保存と定期的な確認。
- データの持ち出し禁止と、バックアップの暗号化。
- AIの読み取り結果は職員が確認してから計画に使う。デモでも、Geminiと職員の設定の違いを画面に出しています。

## 3. 言わないこと

- 公開デモのPASSは合成データ上の計算結果で、現実の安全を保証しません。
- この文書の本番構成は設計の方針で、自治体の環境で検証したものではありません。
