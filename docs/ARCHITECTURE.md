# 設計

## 原則

方策（ルール／Gemini）は**次の行動を選ぶだけ**で、世界状態とPASS/FAILは決定論的なSimulation Coreが管理する。道具が作った計画は必ずCoreで再計算し、方策の出力で判定が変わる経路を作らない。

```text
             ┌──────────── 観測（検証済みの状態から導出・許可行動を含む） ────────────┐
             │                                                                      │
             ▼                                                                      │
  方策（ルール／Gemini／再生）── 判断 ──▶ ガード（許可行動か？）── 実行 ──▶ 道具 ──▶ Simulation Core
                                        │ 許可外・不正出力・障害                     （修復・弱点探索・代替計画）
                                        ▼
                                   停止して記録（fail closed）
```

Coreはモデル SDK、Vertex、HTTPクライアントをimportしない（`tests/test_provider_and_cli.py` の境界テスト）。

## エージェントループ（`packages/agents/loop.py`）

ループが状態（現在の計画とその検証結果、弱点探索・代替計画の結果）を持つ。各ステップで観測 `AgentObservation` を作り、方策に1つの判断 `AgentDecision`（行動＋理由コード）を求める。

### 状態ごとの許可行動

| 状態 | 許可行動 |
|---|---|
| FAIL、未修復 | `run_repair`, `escalate` |
| FAIL、修復済み（候補なし・探索上限） | `escalate` |
| PASS、弱点未探索 | `run_redteam`, `finish`, `escalate` |
| PASS、単一障害点あり・代替計画未作成 | `plan_contingency`, `finish`, `escalate` |
| PASS、上記以外 | `finish`, `escalate` |
| 最終ステップ | 終了系のみ（PASSなら `finish`, `escalate`、FAILなら `escalate`） |

`finish` はFAILの計画では決して許可されない（契約 `AgentObservation` も拒否する）。

### 道具

| 行動 | 道具 | 検証 |
|---|---|---|
| `run_repair` | `propose_repair`：住民ごとに各避難所への到着経路を早い順に探す（道路の再開まで自宅で待つ候補を含む）。避難所の開設前に着く経路は、出発を遅らせて開設時刻に着けるかを検査し、早い経路が閉鎖にかかる場合に備えて避難所ごとに最大4本まで候補を持つ。同着なら道路数の少ない経路。そのうえで定員を考慮して割り当てる（増加路法：選択肢の少ない住民から決め、空きがあれば希望順に使い、どこも満席のときだけ先客を別の選択肢へ移す。受け入れ人数を最大にするが、到着時刻の最適性は保証しない）。キューへの追加は1回あたり50,000で打ち切り（`SearchBudgetExceeded`） | 候補はCoreでPASSしたものだけ採用 |
| `run_redteam` | `single_road_faults`：計画が通る道路を1本ずつ全時間閉鎖して再実行（24本まで）。閉鎖できなかった道路は「未検査」として数える | 各試行をCoreで実行 |
| `plan_contingency` | `plan_contingencies`：FAILになった閉鎖ごとに、閉鎖した世界で修復をやり直す | 閉鎖した世界でCoreがPASSしたものだけ「検証済み」 |

### 結論（`RunOutcome`）

| 結論 | 条件 |
|---|---|
| `verified_robust` | `finish`、計画が通る全道路を検査済みで、どの閉鎖でもPASS |
| `verified_with_contingencies` | `finish`、全道路を検査済みで、FAILになった閉鎖すべてに検証済みの代替計画 |
| `verified_with_residual_risk` | `finish`、未対策の単一障害点または未検査の道路が残る（方策が理由 `accept_residual_risk` で受け入れた場合など） |
| `verified_untested` | `finish`、弱点探索なし |
| `escalated` | `escalate`。PASSの候補があれば人へ渡す |
| `halted_policy_violation` | 許可外の行動、または不正な出力 |
| `halted_model_error` | モデル障害・タイムアウト・呼出し上限 |

現在のエンジンは決まった経路をたどるため、計画が通る道路を全時間閉鎖すると必ずFAILになる。つまり `verified_robust` は将来の再経路化を見越した区分で、実際に意味を持つのは代替計画の有無である。ルール方策は、未対策の弱点・未検査の道路が残る場面や未探索のまま終える場面では `escalate`（`needs_human_judgement`）を選ぶ。リスクの受け入れは方策（Gemini）が理由コード付きで明示した場合だけ起きる。

### 記録と再生

`AgentTrace` は実行ID（非公開サービスのCloud Loggingの各行と同じ `run_id`）・方策名・モデル・プロンプト版・制限値・全ステップ・結論を持つ。`replay_matches()` は記録された判断を `ReplayPolicy` で同じループに流し、観測・道具の結果・ダイジェスト・結論を含めてトレース全体が一致するかを確かめる。公開画面はこれに通ったGeminiの記録だけを表示する（`data/evidence/`）。

再生が保証するのは判断から結果までの整合性で、判断がGeminiの出力であることは保証しない（署名はしていない）。モデル呼出し回数もトレースの値を信用せず、再生中に数え直す（Geminiは判断1回につき1回、呼出し上限で拒否された回は数えない）。

## サービス構成

| サービス | 公開 | 方策 | 役割 |
|---|---|---|---|
| `disaster-agentic-mvp`（`apps/api`） | 認証なし | ルール方策（ライブ実行ではGeminiの結果を再検証して表示） | プレイ画面（`/`、状況を報告する・道路を壊す）と仕組みの説明（`/slides`）、`/v1/showcase`（エージェントの実行記録を含む）、`/v1/agent/care`（Geminiによる事情の読み取り）、`/v1/agent/care/sweep`（一括検算、AIなし）、`/v1/agent/read`（Geminiによる報告の読み取り）、`/v1/agent/live`（Geminiのライブ実行）。Vertex AIの権限を持たない |
| `disaster-agentic-orchestrator`（`apps/orchestrator_service`） | Cloud Run IAMのみ | Gemini（Vertex AI） | `POST /v1/agent/run`：Scenario＋Planを受け、トレースを返す。`POST /v1/care/read`：事情メモと設備を受け、避ける避難所と理由を返す。`POST /v1/report/read`：報告文と道路の一覧を受け、通れない道路のIDを返す |
| `disaster-gemma-runtime`（`apps/gemma_service`） | 非公開（予定） | — | Gemma＋役割別アダプタで住民の行動意図を生成。未接続 |

非公開サービスは呼出し側から `SimulationResult` を受け取らず、すべて自分で計算する。呼出し側がプロンプトに偽のPASS/FAILを注入することはできない。プロンプトに渡す観測は件数・真偽値・エンジンとループのコードだけで、呼出し側が名付けられる計画IDは除く。

### 挑戦モード（`/v1/agent/challenge`、トップのプレイ画面と場面2）

訪問者は固定シナリオの道路を1〜2本選び、全時間通行止めにした世界でエージェント（ルール方策）に立て直させる。道路の閉鎖は弱点探索と同じ `with_road_closed()` で行い、計画はすべてCoreで検証する。選べるのはそのシナリオの道路IDだけで、組合せは有限（基本6通り、川沿いの地区55通り）なので、答えをすべてキャッシュして負荷を抑える。同じ世界は `/v1/agent/live` の `closed_roads` でGeminiにも渡せる。

プレイ画面は返ってきたトレースを1ステップずつ再生し（判断はサーバー側で済んでいる）、弱点探索では調べた道路を順に光らせ、最後に新しい計画で住民の移動を再生する。地図の上の数字（避難できる住民・計画の判定）は、そのステップまでにCoreが返した結果から出す。

修復は全員を受け入れられる場合だけ候補を返す（一部だけの計画は作らない）。橋のように代わりのない道路を断つと、エージェントは計画を作れず人へ引き継ぐ。一部の住民だけを救う計画と、残る住民の引き継ぎは今後の課題。

### 住民の事情の読み取り（`/v1/agent/care` → 非公開 `/v1/care/read`、`packages/agents/care_reader.py`）

川沿いの地区の住民12人（全員架空）には短い事情メモ、避難所3か所には設備の説明がある（`data/demo_area/river_district/care.json`、契約は `packages/domain/care.py`）。

1. プレイ画面が、訪問者の書き換えたメモだけを `POST /v1/agent/care` に送る（1件100文字以内の1行、知らない住民IDは422）。公開サービスが残りのメモと設備を足して、非公開サービスの `/v1/care/read` を呼ぶ（1日の回数を1回使う）。
2. Geminiは全員のメモと設備を1回で読み、「住民ID・避難所ID・理由」の組を返す。答えの型はリクエストごとに作り、住民と避難所はその街のIDの列挙、理由は9つ（段差・坂、所在を守る、夜間の安全、授乳、医療機器の電源、ペット、言語、食事、静かな部屋）の列挙だけ（プロンプトは `care_reader/v2`）。名前・年齢・性別・国籍・出身・宗教・言語だけから事情を推し量らないよう指示している。返った組は非公開側と公開側の両方で確かめる。メモの中身はログに残さず、件数だけを記録する。
3. 返った組は、シナリオの `restrictions`（`packages/domain/models.py` の `ShelterRestriction`）として `/v1/agent/live`・`/v1/agent/challenge` に渡す。Simulation Coreは、制限された避難所への割り当てを `unsuitable_shelter` として拒否し、修復の探索はその避難所を候補に入れない。条件のないシナリオは以前と同じ形で直列化されるので、入力ダイジェストと記録済みの実行は変わらない。
4. 「AIなしで比較」では、職員が同じメモから設定した条件（`reviewed_restrictions`）を使う。

### 住民の入れ替えと一括検算（`/v1/agent/care?pattern=` と `/v1/agent/care/sweep`、`packages/repair/sweep.py`）

川沿いの地区には架空の住民100人のプール（`data/demo_area/river_district/residents.json`、契約は `ResidentPool`）がある。各住民が持つのは名前・年齢・本人の言葉のメモと、職員が設備と照らして設定した「避ける避難所と理由」だけで、出身・国籍・宗教の項目はない。最初の12人は `care.json` の12人と同じ。

1. 組み合わせ（`pattern`、0〜29）は、0が元の12人、それ以外は「シナリオ名・組み合わせ番号・プール内の位置」のSHA-256の順に並べた先頭12人（どの環境でも同じ）。12人は地図の同じ12軒に住み、メモと職員の設定だけが入れ替わる。
2. 一括検算はAIを使わない。30通りそれぞれについて、職員の設定を条件にしたシナリオで元の計画をCoreが判定し、不成立なら修復の探索が全員の計画を探す。見つからなければ理由を付ける：どの避難所の条件にも合わない人がいる（`no_shelter`）／ある避難所の組にしか行けない人が、その定員の合計を超える（`capacity`、ホールの条件）／それ以外（`route`）。
3. 不成立の組み合わせに対し、避難所1か所の変更をすべて試す：ある理由を満たす（その避難所でその理由の条件だけを外す。同じ避難所に別の理由もある人は外れない）か、定員を2人増やす。1つで救える組み合わせの数と、最も多く救える変更を順に3つまで積み重ねた効果を返す。
4. 計算は1秒ほどで、結果はサービス内に保持して使い回す。この数字は合成データとこの探索の性質で、現実の避難所の評価ではない。

### 報告の読み取り（`/v1/agent/read` → 非公開 `/v1/report/read`、`packages/agents/report_reader.py`）

エージェントの「観測」の入口。電話や無線で届くような1行の報告文（例：「橋が冠水して渡れないと消防から連絡」）を、Geminiが街の道路に結びつける。ルールでは扱いにくい自然言語の理解だけをGeminiに任せ、その先はほかの経路と同じ検証を通す。

1. 訪問者がプレイ画面で報告文（120文字以内の1行、制御文字なし）を書き、「Geminiで計画を立て直す」を押す。
2. 公開サービスは、選ばれた固定シナリオの道路の一覧（ID・日本語名・つなぐ2地点、`apps/api/labels.py`）と報告文を、IAM認証で非公開サービスに送る。
3. 非公開サービスは報告文を**データとして**Geminiに渡す（`report_reader/v1` のプロンプトで、報告文の中の指示には従わないよう明示）。応答スキーマはリクエストごとに作り、`closed_roads` は**その街の道路IDの列挙型の配列（最大2件）**だけ。返ってきたIDはここでも、公開サービスでも確かめる。
4. 読み取った道路は画面に表示され、その道路を全時間閉鎖した世界で、ライブ実行（下記）がGeminiにエージェントを動かさせる。計画の成否はCoreが決める。

報告文はプロンプトインジェクションを含みうる前提で設計している。答えの型が道路IDの列挙に限られるため、起こせるのは道路の読み違いまでで、それも画面に出て、計画は検証される。報告文はどちらのサービスのログにも残さず、文字数だけを記録する。読み取りはGeminiの判断なので再生検証はできない（トレースと違い、決定論的に再計算できる部分がない）。

### Geminiのライブ実行（`/v1/agent/live`、`apps/api/live_agent.py`）

1. 訪問者がプレイ画面で「Geminiで計画を立て直す」（または場面9で「Geminiでライブ実行」）を押す。送るのはシナリオ名（`base`／`river_district`）と、閉鎖する道路ID（報告の読み取り結果か、地図での選択）だけ。
2. 公開サービス（専用サービスアカウント `evacweave-public-sa`、プロジェクトのロールなし）が、メタデータサーバーから非公開サービスURLを宛先とするIDトークンを取得し、`POST /v1/agent/run` を呼ぶ。付与しているのは非公開サービスに対する `roles/run.invoker` と、回数を数える非公開バケットに対する `roles/storage.objectUser` だけ。
3. 非公開サービスがVertex AIのGeminiを方策としてループを実行し、トレースを返す。各ステップはCloud Loggingに構造化ログで残り、`run_id` と、公開リクエストから引き継いだトレースIDで相関する。
4. 公開サービスはトレースの方策名とモデル（許可リスト）を確かめ、`replay_matches()` でSimulation Coreに再生して、観測・道具の結果・呼出し回数・結論がすべて一致した場合だけ返す。一致しなければ502で、何も表示しない。

制限：既定で無効（`LIVE_AI_ENABLED=1` で有効）。読み取りと実行で同時1件（2件目は待たせず429）。1日の回数上限 `LIVE_AI_DAILY_RUNS`（既定40。読み取り1回・実行1回をそれぞれ1回と数える。Cloud Run上ではCloud Storageの非公開バケットに1日1オブジェクトで数え、世代番号の条件付き書き込みで二重に取らない。インスタンスが入れ替わっても0回に戻らず、読み書きできなければGeminiを呼ばずに断る。始めた要求は失敗しても返却しない）。期限は実行70秒・報告の読み取り45秒・事情の読み取り66秒（非公開サービスでの打ち切り（実行52秒・報告35秒・事情56秒）より長く、公開サービスのタイムアウト90秒より短い）。事情の読み取りは全員分を1回で答えるため、本番で14〜18秒、遅いときは36秒を超えた（2026-10-14）。そこでこの呼出しだけ50秒まで待つ。リダイレクトは追わず、IDトークンは非公開サービスのオリジンにしか送らない。

プレイ画面の「Google Cloud上の処理の流れ」は、この経路（ブラウザ → 公開Cloud Run → 非公開Cloud Run → Vertex AI Gemini → Simulation Core → Cloud Logging）を、応答に含まれる実際の値（モデル名、読み取り・判断の回数、所要時間、再生検証の結果）で表示する。`run_id` や版は画面に出さず、Cloud Loggingとの照合に使う。「AIなしで比較」では、非公開サービスとGeminiを通らないことをそのまま示す。

## Gemini方策（`packages/agents/orchestrator.py`）

- モデルは許可リスト（`gemini-3.5-flash` 既定、`gemini-3.7-flash`、`gemini-3.8-flash`）。`gemini-2.5-flash` はVertex AIで2026-10-20に退役するため含めない。
- 構造化出力の応答スキーマは列挙型2つ（`GeminiChoice`）だけ。戻り値は厳格な `AgentDecision` で再検証する。
- エージェントの判断は `thinking_level=MINIMAL`（`DECISION_PROFILE`、既定 `minimal`）。短い選択肢から1つ選ぶだけなので深い思考は要らず、`LOW` では2秒だった判断が22秒を超えて打ち切られたことがある（2026-10-14、Vertex 504）。読み取りは `thinking_level=LOW`（`GEMINI_PROFILE`）。Gemini 3系では `thinking_budget` を使わない。出力512トークン、1回25秒、SDKの再試行なし（要求ごとに `attempts=1`）。SDKのタイムアウトも同じ値で、サーバーにも `X-Server-Timeout` で伝える。
- 温度は指定しない（Gemini 3の既定1.0）。Googleは、Gemini 3で温度を1.0未満にすると応答がループしたり性能が落ちたりしうるとして、既定のままにするよう勧めている。以前の0.1では、実際の呼出しが期限まで応答しなかった。
- Vertex AIのエンドポイントは `global`（既定）・`us-central1`・`asia-northeast1` から選ぶ（`GOOGLE_CLOUD_LOCATION`）。HTTP 429はそのエンドポイントの共有の処理枠が埋まっていることを示すため、続く場合は別のエンドポイントに切り替える。合成データのみを扱う。
- 要求の出し方は「プロファイル」で切り替える（非公開サービスの環境変数 `GEMINI_PROFILE`）。どのプロファイルでも、返ってきた値は同じ厳格さで検証する。
  - `default`：応答スキーマ（列挙型）で出力を制約し、思考はLOW
  - `minimal`：応答スキーマで制約し、思考はMINIMAL
  - `json`：JSONだけを求め、スキーマは指示文に含める（スキーマ制約と思考の組合せで応答が止まる場合の回避策）。列挙外の値は、受け取った側で拒否する
- プロンプトは `packages/prompts/orchestrator/v2_system.txt`。トレースに版（`orchestrator/v2`）を記録する。
- 報告の読み取りも同じモデル・同じ設定（`thinking_level=LOW`、25秒）で、出力は思考を含めて1024トークン（自由文を道路に結びつけるため、行動選択より余裕を持たせる）。プロンプトは `packages/prompts/report_reader/v1_system.txt`、1回の読み取りでGemini1回。

### 呼出しの時間配分と記録

時間は要求の到着から数える（非公開サービスのCloud Runタイムアウト60秒）。

1. Geminiのクライアントを先に準備する（SDKの読み込み、サービスアカウントの認証情報の取得）。冷えたインスタンスでは数秒かかるため、どの呼出しの時間にも含めない。準備に失敗したら呼出しをせずに503。
2. 1回の呼出しは25秒まで。SDKも同じ値で要求を打ち切り、再試行はしない（再試行は予算に入っていない課金になる）。
3. 45秒を過ぎたら呼出しを送らず、残り時間が3秒未満なら呼出しを始めない。その時点でループは止まり、`model_budget_exhausted` としてトレースに残る（呼出し回数にも数えない）。
4. 52秒で全体を打ち切る（504）。

各呼出しはCloud Loggingに `gemini_call`（目的・モデル・所要時間・`run_id`）として残り、失敗した呼出しは `gemini_call_failed` として、例外クラスと（ある場合は）HTTPステータスだけを加えて残る。要求そのものが拒否された場合（400）は、何が拒否されたかを決まった語（`error_hint`：`schema_too_complex`・`schema_refused`・`thinking_refused`・`token_limit_refused`・`other`）で添える。SDKの例外メッセージは応答本文を含むため記録しない。プロンプト・報告文・応答・トークンも記録しない。

`POST /v1/diagnostics/gemini`（非公開・IAM）は、`confirm_paid_call: true` を明示した要求にだけ、本番と同じ形の呼出しを**最大1回**行い、失敗した段階（準備・呼出し・応答の形）、例外クラス、HTTPステータス、各段階の所要時間を返す。同時1件、1インスタンス1日3回まで。Cloud Shellからは `scripts/diagnose_gemini.py` で呼ぶ。このスクリプトは、同じ版・同じモデルで失敗した診断を繰り返さない（一時的な429・500・503だけ、10分後に1回。504は期限までの停止として繰り返さない）。`scripts/verify_gemini.sh` は、検証用の非公開サービスへのデプロイ・診断・記録を1回の確認でまとめて行い、429・404のときだけエンドポイントを切り替える。記録用の `scripts/record_gemini_run.py`（最大6回）は、同じ版・同じモデルで診断が成功していなければ実行しない。

## 制限値

| 項目 | 値 |
|---|---|
| ステップ数 | 最大6（最終ステップは終了系のみ） |
| Gemini呼出し | 1実行最大6回、報告の読み取りは1回。失敗した試行も返却しない |
| 1回の呼出し／1実行 | 25秒／45秒以降は呼出しを送らない（要求の到着から数え、同時実行枠の待ち時間とクライアントの準備を含む）。全体の打ち切り52秒、Cloud Runのタイムアウト60秒。道具はワーカースレッドで動くため、期限が来ればその時点で応答を返す |
| 非公開サービスの入力 | 128 KiB、同時2件、最大1インスタンス |
| 修復探索 | キューへの追加50,000回、出発時刻の候補は8つまで |
| 弱点探索 | 計画が通る道路のうち24本まで（超えた分は未検査として残存リスク） |
| 公開サービス | 最小0・最大1インスタンス、同時4件、90秒（ライブ実行のため）、任意入力のシミュレーションは既定で無効 |
| Geminiのライブ実行 | 既定で無効。固定シナリオのみ、同時1件、1日 `LIVE_AI_DAILY_RUNS` 回（既定40、読み取りと実行で共有）、1実行あたりGemini最大6回・1読み取りあたり1回 |
| 報告文 | 120文字以内の1行。Geminiが返せるのはその街の道路IDだけ（最大2本）。ログには文字数のみ |

これらはCloud Billingの予算や割り当ての代わりではない（[COST_GUARD.md](../infra/cloud-run/COST_GUARD.md)）。

## 2D避難ラボ（`/lab`）

ブラウザ内で合成の地区を生成し、遺伝的アルゴリズムで住民の行動案を探索してCanvasで再生する対話型デモ（[EVAC_LAB.md](EVAC_LAB.md)）。サーバー側の計算やモデル呼び出しはない。JSの判定は参照実装で、書き出したJSONを `scripts/check_lab_export.py` でPython Coreと照合する（CIでも固定シードで照合）。

## Gemma（今後の工程）

Google ColabでGemma 4を4-bit QLoRAし、役割ごとにPEFTアダプタを作る（`training/colab/`）。推論サービスは住民役（`MoveDecisionRequest` → `MoveDecisionResponse`）だけを契約として実装済みで、出力した行動意図は必ずCoreで検証する。本番には接続していない。

## Simulation v1 の前提

時間は整数秒、道路は有向辺。移動時間は入力の定数。閉鎖は既知の固定期間で、半開区間 `[start, end)` として検査する。期限ちょうどの到着は許可する。避難所の定員は到着順、同時到着は `actor_id` 順で、この順序は公平性の主張ではない。同じ契約入力・同じエンジン版なら結果は同一。
